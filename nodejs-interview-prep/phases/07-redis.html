Phase 07 · Low-latency state with explicit failure modes

Redis

Use Redis for caching, coordination, limits, and sessions without mistaking a fast distributed system for a correctness boundary.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Redis fundamentals

High
Concept

Redis is an in-memory data-structure server with single-threaded command execution per shard, optional persistence, replication, clustering, and atomic commands/scripts.

Why it works this way

Low latency comes from memory and efficient structures, but durability, failover, hot keys, and memory eviction must be designed explicitly.

Running example
Example
SET order:101:status paid
GET order:101:status
INFO memory
INFO replication
Expected:
Fast does not mean durable or strongly consistent across failover
Common mistakes / interview traps
  • Treating Redis fundamentals as a library setting instead of defining its failure and consistency behavior.
  • Ignoring retries, concurrency, observability, and trust boundaries in production.
Interview questions
  • How would you apply Redis fundamentals to an order/payment API?
  • What failure mode changes your design for Redis fundamentals?
Reveal model answers
Redis fundamentals should be explained as a contract: state the invariant, the mechanism that preserves it, and the behavior under retry or partial failure.
For orders and payments, I make ownership, consistency boundaries, and externally visible errors explicit, then instrument the important decisions.
Senior follow-ups
  • What trade-off would make you reject the default Redis fundamentals approach?
  • How would you roll this out and prove it behaves correctly?
Reveal senior-level answers
I compare correctness, latency, operability, and cost. I prefer the simplest mechanism that preserves the business invariant and has a safe degradation path.
I use compatibility tests, staged rollout, metrics by outcome, structured audit events, and a rollback path; load and fault tests cover retries and dependency failure.

TTL

High
Concept

TTL sets automatic expiry in seconds or milliseconds. Expiry is metadata on the key and may be refreshed, preserved, or removed by writes depending on the command.

Why it works this way

TTL bounds staleness and memory but is not precise scheduling or guaranteed immediate deletion.

Running example
Example
SET order:101:summary '{...}' EX 60
TTL order:101:summary
EXPIRE order:101:summary 120 GT
Expected:
Positive TTL counts down; -1 means no expiry; -2 means absent
Common mistakes / interview traps
  • Treating TTL as a library setting instead of defining its failure and consistency behavior.

Cache-aside

High
Concept

The application reads cache, falls back to the database on miss, then populates cache; writes update the database and invalidate or refresh cache.

Why it works this way

Only requested data is cached and cache failure can degrade to the source, but races can reinsert stale data.

Running example
Node.js
let order = await redis.get(key);
if (!order) {
  order = await db.order.findUnique({ where: { id } });
  await redis.set(key, JSON.stringify(order), { EX: 60 });
}
return JSON.parse(order);
Expected:
Hit avoids DB; miss populates a bounded-TTL entry

Write-through

High
Concept

Writes synchronously update the system of record and cache before success is returned, with an explicit ordering and compensation policy.

Why it works this way

Reads stay warm, but dual writes cannot be atomic across Redis and the database without accepting or repairing inconsistency.

Running example
Example
1. Commit order to PostgreSQL
2. SET cache value with TTL
3. If cache write fails, return success and invalidate/retry asynchronously
Expected:
Database remains source of truth

Write-behind

High
Concept

Writes land in a cache or durable buffer and are persisted asynchronously in batches.

Why it works this way

It reduces write latency and enables batching but risks data loss, reorder, and harder recovery; plain Redis cache is rarely suitable for payment truth.

Running example
Example
Client → durable stream → acknowledged
Worker batches updates → database
Track offsets, retries, poison records, and idempotency
Expected:
Do not use volatile write-behind for financial state

High
Concept

A distributed cache partitions and replicates entries across nodes. Clients must handle topology, failover, serialization versions, and partial outages.

Distributed locks

High
Concept

A Redis lock commonly uses SET key token NX PX ttl and a compare-token-and-delete Lua script. The lease can expire while work continues.

Why it works this way

The random token prevents deleting another owner's lease, but a lock alone cannot protect a correctness-critical resource from paused or partitioned clients.

Running example
Example
SET lock:order:101 <random-token> NX PX 5000
-- release atomically only if GET(key) == token
-- pass a monotonic fencing token to the protected store

Use database constraints/transactions for payment invariants; fencing for stale owners

Sessions

High
Concept

Store opaque session records in Redis with TTL, rotate IDs after authentication or privilege change, and index user sessions for revocation.

Why it works this way

Redis provides shared low-latency session state, while expiry and deletion support logout and revocation.

Running example
Example
SET session:<sha256-id> '{"userId":17,"roles":["buyer"]}' EX 1800
SADD user:17:sessions <sha256-id>
On logout: DEL + SREM
Expected:
Cookie contains only an opaque Secure HttpOnly session ID

Pub/Sub

High
Concept

Redis Pub/Sub delivers transient messages to currently connected subscribers with no replay, acknowledgement, or consumer state.

Why it works this way

It is useful for ephemeral notifications and invalidation hints, not durable order/payment processing.

Running example
Example

SUBSCRIBE cache-invalidate

Disconnected subscribers miss messages; use Streams/queue for durable work

High
Concept

Cache normalized expensive responses by tenant, authorization-sensitive inputs, API version, and query fingerprint; use TTL, bounds, and negative caching selectively.

Stale cache

High
Concept

Staleness is controlled with TTL, versioned keys, write invalidation, event-driven invalidation, and explicit stale-while-revalidate windows.

Why it works this way

Perfect invalidation across stores is expensive; define an acceptable staleness budget per field and operation.

Running example
Example
Cache value: { version: 8, cachedAt: ..., order: ... }
DB commit emits order.updated(version=9)
Consumer deletes only cached versions < 9

Payment status may require primary read; catalog copy can tolerate staleness

Prevent cache stampede

High
Concept

Use request coalescing/single-flight, short fill locks, TTL jitter, stale-while-revalidate, and proactive refresh for hot keys.

Why it works this way

When a hot key expires, simultaneous misses can overload the database and prolong the outage.

Running example
Example
On miss:
- one owner gets fill:order:101 lease
- others serve bounded stale value or wait briefly
- owner populates with TTL 60s + random(0..10s)
Expected:
Lock owner uses timeout; all paths have backpressure

Distributed locking scenario

High
Concept

For a scheduled order reconciliation, use a bounded lease for duplicate-work reduction, an owner token, renewal, and idempotent work; use fencing or database state for correctness.

Why it works this way

Process pauses and network partitions can create two apparent owners, so the protected system must reject stale writers.

Running example
Example
Acquire lease + increment fencing counter → fence=43
UPDATE orders SET ... WHERE id=101 AND last_fence < 43
Store last_fence=43 atomically
Expected:
Lease limits coordination; fencing enforces ordering
