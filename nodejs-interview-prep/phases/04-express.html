Phase 04 · HTTP application design

Express & API Architecture

Build secure, observable Express boundaries around testable order and payment use cases, including failure and scaling concerns.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Express architecture

High
Concept

Express is a thin ordered router/middleware pipeline around Node HTTP. Keep transport adaptation separate from application and domain policy.

Why it works this way

Thin infrastructure boundaries prevent request objects, status codes, and framework lifecycle from leaking through the order/payment core.

Running example
Node.js
const layers = ["route", "validation", "controller", "service", "repository"];
console.log(layers.join(" -> "));
Expected:
route -> validation -> controller -> service -> repository
Common mistakes / interview traps
  • Explaining Express architecture only by syntax and not by runtime behavior.
  • Ignoring failure modes, observability, and the order/payment-service impact.
Interview questions
  • Explain Express architecture and give a production example.
  • What bug would reveal a weak understanding of Express architecture?
Reveal model answers
Express architecture is not just syntax; I explain its runtime mechanism, then show where it affects correctness or latency in an order or payment flow.
I would reproduce the behavior with a minimal case, add focused telemetry, and verify the fix under concurrency rather than relying on intuition.
Senior follow-ups
  • What trade-offs would make you avoid or constrain Express architecture in a high-throughput service?
  • How would you test and observe this behavior in production?
Reveal senior-level answers
I choose based on correctness, operational cost, team familiarity, and measurable workload characteristics. I make assumptions explicit and preserve a rollback path.
I use deterministic unit tests where possible, integration tests at boundaries, load or fault tests for concurrency, and metrics plus structured logs for production evidence.

Middleware

High
Concept

Middleware runs in registration order and must end the response, call next(), or pass an error. Prefer narrow cross-cutting responsibilities.

Why it works this way

The chain composes reusable transport concerns, but hidden ordering dependencies and double completion cause fragile behavior.

Running example
Node.js
const chain = [req => (req.trace="t1"), req => (req.user="u1")];
const req = {}; chain.forEach(fn => fn(req)); console.log(req.trace, req.user);
Expected:
t1 u1

Authorization

High
Concept

Authorization decides whether a verified principal may perform an action on a resource, including tenant and ownership constraints.

Why it works this way

Central policy avoids scattered role checks and protects against IDOR where authenticated users access another account's orders.

Node.js

Request validation

High
Concept

Validate params, query, headers, and bodies at the edge; reject unknown or malformed data with stable machine-readable errors.

Controllers

High
Concept

Controllers adapt HTTP input to use-case calls and map results to HTTP. They should not own pricing, transaction, or provider policy.

Why it works this way

A thin controller is easy to contract-test and lets the same application use case serve jobs, GraphQL, or CLI adapters.

Running example
Node.js
const controller = async (req, service) => ({ status: 201, body: await service.create(req.body) });
console.log(typeof controller);

function

Dependency injection

Medium
Concept

Construct services with explicit dependencies at a composition root; avoid importing mutable singletons inside domain code.

Why it works this way

Explicit dependencies improve tests and lifecycle control without requiring a heavyweight container.

Running example
Node.js
const makeService = ({ clock }) => ({ now: () => clock.now() });
console.log(makeService({clock:{now:()=>42}}).now());

42

High
Concept

Create request context early, emit structured completion logs, correlate downstream calls, and redact authorization, cookies, and payment data.

console.log(JSON.stringify(log));

Pagination

High
Concept

Offset pagination is simple but unstable and costly at depth; cursor/keyset pagination uses a deterministic unique ordering and opaque cursor.

Why it works this way

Keyset queries continue from indexed values, avoiding skipped/duplicated rows during concurrent order creation.

Node.js

console.log(rows.filter(x => x.id < 3).slice(0,1)[0].id);

2

Medium
Concept

Why it works this way

Why it works this way

Providers retry and deliver out of order; durable idempotent ingestion separates availability from business processing.

Background jobs

High
Concept

Use durable queues for slow or retryable work, with idempotent handlers, bounded retries, backoff, dead-lettering, and observability.

Why it works this way

HTTP request lifetimes are poor owners for email, reconciliation, and provider retries; durable queues survive process restarts.

Bad vs good architecture

High
Concept

Bad architecture mixes validation, SQL, payment calls, policy, and response mapping in one route. Good architecture uses thin adapters, explicit use cases, domain rules, and replaceable infrastructure.

Why it works this way

Separation is valuable when it clarifies ownership, testing, and transactions—not as folder ceremony. Dependencies should point toward stable policy.

Running example
Node.js
const good = ["route", "controller", "checkoutUseCase", "repositories/gateways"];
console.log(good.join(" -> "));

route -> controller -> checkoutUseCase -> repositories/gateways
