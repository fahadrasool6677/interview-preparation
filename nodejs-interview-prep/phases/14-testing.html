Phase 14 · Confidence engineering

Testing

Choose test boundaries by risk, verify real contracts, and keep asynchronous systems deterministic.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Unit testing

High
Concept

Unit tests exercise a small behavior through a stable public interface with fast, deterministic collaborators.

Why it works this way

They localize failures and support refactoring when they assert outcomes rather than implementation details.

Running example
Node.js
function total(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
test('calculates an order total', () => {
  expect(total([{ price: 12, quantity: 2 }])).toBe(24);
});
Common mistakes / interview traps
  • Explaining Unit testing as syntax or tooling without discussing its runtime behavior.
  • Ignoring observability, rollback, resource limits, and failure recovery.
Interview questions
  • Where does Unit testing fit in a production Node.js system?
  • What failure mode would make you reconsider your Unit testing design?
Reveal model answers
Unit testing should solve a specific operational or engineering constraint. I would state that constraint, describe the mechanism, and then show how I verify the result in production.
I would reconsider the design when its failure domain, operating cost, or recovery time no longer meets the service's SLOs.
Senior follow-ups
  • How would you operate Unit testing safely during a partial outage?
  • Which metrics and trade-offs matter most for Unit testing?
Reveal senior-level answers
Prefer bounded retries, explicit timeouts, graceful degradation, and a tested rollback path. Preserve enough telemetry to distinguish application, dependency, and infrastructure failures.
Measure user-visible latency and errors first, then saturation, capacity, cost, and recovery time. Optimize only after identifying the binding constraint.
Exercise

Unit-test a pricing policy using boundary values, invalid data, and table-driven cases without testing private functions.

Integration testing

High
Concept

Integration tests verify contracts across real boundaries such as application-to-database, queue, filesystem, or HTTP adapter.

Why it works this way

Many production defects live in serialization, schema, transaction, and configuration boundaries that mocks cannot faithfully reproduce.

Running example
Node.js
beforeAll(async () => db.migrate.latest());
afterEach(async () => db('orders').truncate());
test('persists an order atomically', async () => {
  const order = await repository.create({ customerId: 'c1', total: 42 });
  expect(await db('orders').where({ id: order.id }).first()).toMatchObject({ total: 42 });
});

End-to-end testing

High
Concept

End-to-end tests exercise a critical user flow through deployed system boundaries, from public interface to durable effects.

Why it works this way

They provide high confidence in wiring and contracts but are slower and harder to diagnose, so keep the suite focused on high-value journeys.

Jest

High
Concept

Jest provides test discovery, assertions, spies, mocks, fake timers, coverage, and worker isolation for JavaScript and TypeScript projects.

Why it works this way

A coherent runner shortens feedback, but global state, leaked handles, module mocking, and parallel execution can create false confidence or flaky tests.

Running example
Node.js
afterEach(() => {
  jest.restoreAllMocks();
  jest.useRealTimers();
});
test('expires cached data', () => {
  jest.useFakeTimers();
  const cache = createCache({ ttlMs: 1000 });
  cache.set('x', 1);
  jest.advanceTimersByTime(1001);
  expect(cache.get('x')).toBeUndefined();
});

Mocking

High
Concept

Mocking replaces a collaborator and can control responses or verify interactions. Mock at architectural seams, not arbitrary internal calls.

Why it works this way

Mocks make rare failures deterministic, but they can drift from real contracts and couple tests to implementation.

Running example
Node.js
const paymentGateway = { charge: jest.fn().mockResolvedValue({ id: 'p1' }) };
const service = new CheckoutService({ paymentGateway });
await service.checkout(order);
expect(paymentGateway.charge).toHaveBeenCalledWith({ amount: order.total, idempotencyKey: order.id });

Test doubles

High
Concept

A dummy fills an unused parameter, a stub returns canned data, a spy records calls, a mock encodes interaction expectations, and a fake provides a working simplified implementation.

Why it works this way

Naming the double clarifies the test's purpose and warns about fidelity. An in-memory fake is useful but may not reproduce database constraints or concurrency.

stub: clock.now() returns a fixed instant

mock: expects one payment charge

API testing

High
Concept

API tests validate status, headers, body schema, authentication, idempotency, pagination, validation, and error contracts through the HTTP boundary.

Why it works this way

Clients depend on protocol behavior, not controller internals. Contract-focused tests detect accidental breaking changes.

Running example
Node.js
const response = await request(app)
  .post('/orders')
  .set('Idempotency-Key', 'test-key-1')
  .send({ sku: 'A1', quantity: 2 });
expect(response.status).toBe(201);
expect(response.headers.location).toMatch(/^\/orders\//);
expect(response.body).toMatchObject({ status: 'pending' });

Test coverage

High
Concept

Coverage measures executed statements, branches, functions, and lines; mutation testing measures whether tests detect behavioral changes.

Why it works this way

Coverage finds unexercised code but cannot prove meaningful assertions. Branch risk and mutation survival are stronger guides than a single percentage target.

Running example
Example

npx stryker run

Testing asynchronous code

High
Concept

Async tests must return or await the promise, control time explicitly, and observe eventual effects without arbitrary sleeps.

Why it works this way

Unawaited work creates false positives and open handles. Polling with a deadline or fake timers makes eventual behavior deterministic.

Running example
Node.js
test('retries once after a transient error', async () => {
  const operation = jest.fn()
    .mockRejectedValueOnce(new Error('temporary'))
    .mockResolvedValue('ok');
  await expect(retry(operation, { attempts: 2, delayMs: 0 })).resolves.toBe('ok');
  expect(operation).toHaveBeenCalledTimes(2);
});

What should and should not be mocked

High
Concept

Mock nondeterministic or expensive external boundaries when testing application policy: payment providers, clocks, random IDs, email, and remote APIs. Do not mock the code under test, plain value objects, or database behavior in tests intended to validate SQL.

Why it works this way

The goal is deterministic tests without inventing a parallel implementation of reality. Use real local infrastructure for contracts and mocks for controlled application-level scenarios.

Running example
Example
Usually mock: remote payment API, email gateway, clock, UUID source
Usually real: domain functions, serializers, repository SQL in integration tests
Use both: mock remote adapter in service tests + provider contract/sandbox tests
Common mistakes / interview traps
  • Mocking every dependency until the test only verifies mock wiring.
  • Calling real third-party services from the fast unit suite.
  • Using an in-memory fake as proof that production SQL and locking work.
