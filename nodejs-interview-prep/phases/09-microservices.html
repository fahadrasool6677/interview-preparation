Phase 09 · Distributed architecture

Microservices

Choose service boundaries and communication semantics deliberately, then design for partial failure, duplication, and operational ownership.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Monolith vs microservices

High
Concept

A modular monolith deploys one unit; microservices add independent deployment and failure boundaries across a network.

Why it works this way

Distribution buys team and scaling autonomy but adds latency, consistency, testing, and on-call cost. Start with constraints, not fashion.

Running example
Example
Decision: independently scale checkout and search only after module ownership and release contention become measurable.
Common mistakes / interview traps
  • Treating monolith vs microservices as a product choice without measuring its operational cost.
  • Explaining only the happy path; senior answers include overload, partial failure, and recovery.
Interview questions
  • Explain monolith vs microservices and when you would use it.
  • What production signal tells you this design is failing?
Reveal model answers
Model answer: A modular monolith deploys one unit; microservices add independent deployment and failure boundaries across a network. I would define the SLO, instrument the critical path, and validate the decision under realistic load before standardizing it.
Failure signal: Watch latency percentiles, error/timeout rate, saturation, backlog, and business-level correctness—not averages alone.
Senior follow-ups
  • How does this behave during a partial outage or retry surge?
  • Which trade-off would make you reverse this decision?
Reveal senior-level answers
Bound concurrency and retries, use deadlines and backpressure, preserve idempotency, and make degradation explicit. Recovery must be tested, not assumed.
Reverse the choice when measured complexity, tail latency, consistency risk, or on-call burden exceeds the isolation or scaling benefit.

Service boundaries

High
Concept

A boundary should follow a business capability with cohesive data and a clear owner, not a technical layer.

REST between services

High
Concept

REST exposes resource-oriented HTTP contracts with status codes, deadlines, authentication, and versioning.

Why it works this way

It is interoperable and observable, but callers must budget connection setup, serialization, retries, and downstream latency.

Running example
Node.js
const r = await fetch(url, {
  signal: AbortSignal.timeout(300),
  headers: { 'x-request-id': traceId }
});
if (!r.ok) throw new Error(`payment: ${r.status}`);

High
Concept
