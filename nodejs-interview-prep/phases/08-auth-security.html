JWT

High
Concept

JWTs are signed claim containers. Pin allowed algorithms and validate signature, issuer, audience, expiry/not-before, token type, and required claims.

Why it works this way

A valid signature proves issuer possession of a key, not user authorization, confidentiality, freshness, or correct audience.

Running example
Example
Header: alg=RS256, kid=key-2026-08
Claims: iss=id.example, aud=orders-api, typ=access, exp=...
Verify against cached JWKS with rotation and unknown-kid refresh limits
Expected:
Reject none, unexpected algorithms, wrong audience, expiry, or token type
Common mistakes / interview traps
  • Attack → control: alg confusion, forged or cross-service token → pin algorithms and validate iss/aud/typ with managed keys.
  • Trusting client-visible claims or identifiers without server-side authorization.
Interview questions
  • How would you apply JWT to an order/payment API?
  • What failure mode changes your design for JWT?
Reveal model answers
Attack → control: alg confusion, forged or cross-service token → pin algorithms and validate iss/aud/typ with managed keys.
I treat JWT as one layer: authenticate the principal, authorize this action on this object, constrain lifetime/scope, and make revocation and detection operational.
Senior follow-ups
  • What trade-off would make you reject the default JWT approach?
  • How would you roll this out and prove it behaves correctly?
Reveal senior-level answers
I compare correctness, latency, operability, and cost. I prefer the simplest mechanism that preserves the business invariant and has a safe degradation path.
I use compatibility tests, staged rollout, metrics by outcome, structured audit events, and a rollback path; load and fault tests cover retries and dependency failure.

OAuth 2.0

High
Concept

OAuth 2.0 is delegated authorization. Authorization Code + PKCE is the default user flow; Client Credentials serves machine identities.

Why it works this way

It separates credential handling, consent, clients, authorization servers, and resource servers.

Running example

OpenID Connect

High
Concept

OIDC adds authentication and identity claims to OAuth via an ID token, UserInfo endpoint, discovery, nonce, and standardized subject semantics.

Why it works this way

It lets a client verify an authentication event while access tokens remain intended for APIs.

Running example
Example
Client validates ID token: iss, aud, azp, exp, nonce
API validates access token: aud=orders-api, scope
Stable identity key: (iss, sub)
Expected:
ID token authenticates to client; access token authorizes API
Common mistakes / interview traps

Access and refresh tokens

High
Concept

Access tokens are short-lived and audience/scoped; refresh tokens are longer-lived authorization-server credentials that should rotate with reuse detection.

Why it works this way

Separating lifetimes limits bearer replay while preserving sessions.

Running example
Example
Access: memory, 5–15 min, aud=orders-api
Refresh: Secure HttpOnly cookie, rotated per use
Reuse of old refresh token: revoke family and require login
Expected:
Never persist browser access tokens in localStorage when a safer BFF/session design is available
Common mistakes / interview traps
  • Attack → control: stolen bearer/refresh token → short access TTL, sender constraint where possible, secure storage, refresh rotation and family revocation.

Password hashing

High
Concept

Password storage uses a salted, deliberately expensive password KDF and stores its encoded parameters with the hash; optional pepper is held outside the database.

Why it works this way

Offline attackers can test guesses without rate limits, so per-guess cost and unique salts reduce throughput and precomputation.

Running example
Node.js
const hash = await argon2.hash(password, {
  type: argon2.argon2id, memoryCost: 65536, timeCost: 3, parallelism: 1
});
const ok = await argon2.verify(hash, candidate);
Expected:
Calibrate to an acceptable server latency and rehash when parameters age
Common mistakes / interview traps
  • Attack → control: stolen password database → Argon2id/bcrypt with calibrated cost, unique salts, optional managed pepper, breached-password checks.
  • Trusting client-visible claims or identifiers without server-side authorization.

bcrypt and Argon2

High
Concept

Argon2id is a modern memory-hard default. bcrypt is mature but has a 72-byte input limit and primarily raises CPU cost.

Why it works this way

Algorithm choice and calibrated parameters determine resistance to GPU/ASIC cracking and server-side denial of service.

Running example
Example
Argon2id: benchmark memory/time/parallelism in production class hardware
bcrypt: cost benchmark + explicit max input handling
On login: verify old hash, then opportunistically rehash
Expected:
Versioned encoded hashes permit gradual migration
Common mistakes / interview traps
  • Attack → control: GPU cracking → prefer calibrated Argon2id memory/time cost; for bcrypt enforce input handling and a strong cost.

Sessions

High
Concept

Server-side sessions map a high-entropy opaque ID to identity, authentication context, expiry, and authorization version; rotate on privilege changes.

Why it works this way

Running example

RBAC

High
Concept

Role-based access control assigns permissions to roles and roles to principals. Roles should represent stable job functions, not every contextual exception.

Why it works this way

RBAC simplifies administration but can cause role explosion and does not replace object ownership or tenant checks.

Running example
Node.js
authorize(user, 'order:refund', order, ({ roles, tenantId }, resource) =>
  roles.includes('support_refunds') && tenantId === resource.tenantId
);
Expected:
A role permits the action; resource context constrains the target
Common mistakes / interview traps
  • Attack → control: horizontal/vertical privilege escalation → centralized deny-by-default policy using role permission plus tenant/object conditions.

High
Concept

API keys identify a calling project or service and should be random, scoped, hashed at rest, prefixed for identification, rotatable, and separately rate-limited.

Never put API keys in URLs or browser-delivered code

High
Concept

TLS authenticates the server and encrypts/integrity-protects transport. Modern configurations use TLS 1.2/1.3, valid certificates, safe ciphers, HSTS, and correct proxy termination.

Why it works this way

Without TLS, credentials and responses can be observed or modified; application signatures do not generally replace channel security.

Running example
Example

TLS protects transit, not compromised endpoints, logs, or authorization flaws
