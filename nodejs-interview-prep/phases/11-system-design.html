Phase 11 · Architecture interviews

System Design

Start with requirements and estimates, define invariants and SLOs, then evolve the design around bottlenecks and failure modes.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Requirements gathering

High
Concept

Clarify actors, workflows, scope, constraints, and success metrics before drawing boxes.

Why it works this way

Architecture is only defensible against explicit requirements and assumptions.

Running example
Example
Ask: daily active users, read/write ratio, geography, retention, payload size, peak factor, compliance, and launch scope.
Common mistakes / interview traps
  • Treating requirements gathering as a product choice without measuring its operational cost.
  • Explaining only the happy path; senior answers include overload, partial failure, and recovery.
Interview questions
  • Explain requirements gathering and when you would use it.
  • What production signal tells you this design is failing?
Reveal model answers
Model answer: Clarify actors, workflows, scope, constraints, and success metrics before drawing boxes. I would define the SLO, instrument the critical path, and validate the decision under realistic load before standardizing it.
Failure signal: Watch latency percentiles, error/timeout rate, saturation, backlog, and business-level correctness—not averages alone.
Senior follow-ups
  • How does this behave during a partial outage or retry surge?
  • Which trade-off would make you reverse this decision?
Reveal senior-level answers
Bound concurrency and retries, use deadlines and backpressure, preserve idempotency, and make degradation explicit. Recovery must be tested, not assumed.
Reverse the choice when measured complexity, tail latency, consistency risk, or on-call burden exceeds the isolation or scaling benefit.

Sketch a production-ready use of requirements gathering. Include SLOs, telemetry, one failure injection, and a rollback or recovery path.

URL shortener

Design

Design redirects optimized for extreme read volume while keeping creation correct and abuse-resistant.

Requirements

  • Create custom or generated aliases
  • Redirect with low p99 latency
  • Expiration, analytics, and abuse controls

APIs

  • POST /v1/links {url, customAlias?, expiresAt?}
  • GET /:alias → 301/302
  • GET /v1/links/:alias/stats

Database schema

  • links(alias PK, destination, ownerId, createdAt, expiresAt, status)
  • click_events(eventId, alias, timestamp, region, referrer)

Architecture

  • API generates Base62 IDs or claims custom aliases transactionally
  • Cache/edge redirect path; database is source of truth
  • Clicks enter an asynchronous analytics stream

Scaling strategy

  • Partition by alias hash
  • Cache hot links at edge with negative-cache care
  • Aggregate analytics asynchronously

Failure scenarios

  • Cache serves a disabled malicious link
  • ID generator region failure
  • Hot celebrity alias overloads one partition

Bottlenecks

  • Hot keys and cache misses
  • Analytics cardinality and bot traffic

Trade-offs

  • 301 caches aggressively but is hard to revoke; 302 preserves control
  • Random IDs reduce predictability but cost more bytes

Interview questions

  • How do you guarantee custom-alias uniqueness?
  • How do deletion and cache invalidation work?

WhatsApp-like messaging

Design

Design durable one-to-one and group messaging with offline delivery and per-device state.

Requirements

  • Send text/media, groups, ordering per conversation
  • Offline sync, delivered/read receipts
  • End-to-end encryption assumptions

APIs

  • WebSocket SendMessage(clientMessageId, conversationId, ciphertext)
  • GET /sync?cursor=...
  • POST /media/upload-url

Database schema

  • messages(conversationId, sequence, messageId, senderId, ciphertext)
  • device_cursors(deviceId, conversationId, lastSequence)
  • memberships(conversationId, userId, role)

Architecture

  • Gateway maintains connections and authenticates devices
  • Sequencer assigns per-conversation order; durable log fans out
  • Push notification wakes offline devices; object storage holds media

Scaling strategy

  • Partition by conversationId; split exceptionally large groups
  • Multi-region home routing and async replication
  • Batch fan-out and sync

Failure scenarios

  • Gateway disconnect during send yields ambiguous result
  • Offline device falls behind retention
  • Membership change races with send

Bottlenecks

  • Celebrity groups, connection count, receipt fan-out

Trade-offs

  • Fan-out-on-write accelerates reads but amplifies large groups
  • Strict global ordering is rejected for per-conversation ordering

Interview questions

  • How are duplicates removed across reconnects?
  • How do membership and encryption-key rotation interact?

E-commerce system

Design

Design catalog, cart, checkout, inventory, order, and payment boundaries around explicit business invariants.

Requirements

  • Browse/search products
  • Cart and checkout
  • Reserve finite stock and process payment
  • Track and cancel orders

APIs

  • GET /products?query=
  • PUT /carts/:id/items
  • POST /orders {cartId,idempotencyKey}
  • GET /orders/:id

Database schema

  • products, sku_inventory(available,reserved,version)
  • orders, order_items, payments
  • outbox and processed_events

Architecture

  • Catalog/search read models are eventually consistent
  • Checkout orchestrates inventory reservation and payment authorization as a saga
  • Order database and outbox commit together

Scaling strategy

  • Shard orders by customer/tenant
  • Partition inventory commands by SKU
  • CDN images and cache product reads

Failure scenarios

  • Payment succeeds but response is lost
  • Reservation expires during payment
  • Search displays stale price

Bottlenecks

  • Flash-sale hot SKU, payment dependency, oversized carts

Trade-offs

  • Reserve-first avoids oversell but can strand stock
  • Strong inventory writes with eventually consistent catalog reads

Interview questions

  • Prevent double charge and oversell.
  • Where is the source of truth for price at checkout?
