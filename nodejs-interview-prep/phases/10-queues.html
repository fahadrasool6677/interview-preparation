Queues & Event-Driven Systems

Reason about delivery through one production pipeline: Order Created → Payment → Inventory → Notification. Every stage must tolerate retries, duplicates, delay, and partial failure.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Queue vs Pub/Sub

High
Concept

A queue distributes each job to one consumer group; Pub/Sub gives each subscription its own delivery.

Why it works this way

Choose from delivery semantics: work sharing versus independent fan-out, not from vendor terminology.

Running example
Example
Order Created → Payment → Inventory → Notification
Queue: payment workers compete for Order Created.
Pub/Sub: payment, analytics, and fraud each receive Order Created.
Common mistakes / interview traps
  • Treating queue vs pub/sub as a product choice without measuring its operational cost.
  • Explaining only the happy path; senior answers include overload, partial failure, and recovery.
Interview questions
  • Explain queue vs pub/sub and when you would use it.
  • What production signal tells you this design is failing?
Reveal model answers
Model answer: A queue distributes each job to one consumer group; Pub/Sub gives each subscription its own delivery. I would define the SLO, instrument the critical path, and validate the decision under realistic load before standardizing it.
Failure signal: Watch latency percentiles, error/timeout rate, saturation, backlog, and business-level correctness—not averages alone.
Senior follow-ups
  • How does this behave during a partial outage or retry surge?
  • Which trade-off would make you reverse this decision?
Reveal senior-level answers
Bound concurrency and retries, use deadlines and backpressure, preserve idempotency, and make degradation explicit. Recovery must be tested, not assumed.
Reverse the choice when measured complexity, tail latency, consistency risk, or on-call burden exceeds the isolation or scaling benefit.

Producers

High
Concept

A producer creates a durable event with stable identity, version, timestamp, and partition key.

Why it works this way

Transactional outbox publishing avoids the database-commit/message-publish dual-write gap.

Running example
Node.js
await db.transaction(async tx => {
  await tx.orders.insert(order);
  await tx.outbox.insert({
    eventId, type: 'OrderCreated.v1', key: order.id, payload
  });
});
// relay publishes outbox rows after commit

High
Concept

Acknowledgements

High
Concept

An acknowledgement transfers responsibility back to the broker after successful durable processing.

Why it works this way

Acknowledging too early loses work; too late increases duplicates. Visibility/lock time must exceed normal processing or be renewed.

Running example
Example
Payment commits authorization and outbox event, then ACKs OrderCreated. A crash before ACK causes safe redelivery.

Message ordering

High
Concept

Ordering is scoped to a partition key such as orderId and requires bounded per-key concurrency.

Why it works this way

A global order destroys parallelism; a per-order sequence preserves state transitions.

Order Created → Payment → Inventory → Notification
Partition by orderId: OrderCreated(seq=1) precedes PaymentAuthorized(seq=2); different orders run concurrently.

At-least-once

High
Concept

A message is retried until acknowledged, so loss is minimized but duplicate delivery is possible.

Why it works this way

At-most-once

High
Concept

A message is delivered zero or one time by acknowledging before work or never retrying.

Why it works this way

It avoids duplicates by accepting loss; suitable only where missing work is tolerable or reconstructable.

Running example
Example
Best-effort analytics for OrderCreated may be at-most-once; payment and inventory must not be.

Exactly-once concepts

High
Concept

Exactly-once is scoped: a broker may atomically manage its log, while external database, email, and payment effects remain separate.

Why it works this way

Order Created → Payment → Inventory → Notification

Idempotent consumers

High
Concept

An idempotent consumer stores message identity or enforces the business invariant in the same transaction as its effect.

Why it works this way

A check-then-act outside the transaction races under concurrent duplicate deliveries.

Running example
Node.js
await db.transaction(async tx => {
  const claimed = await tx.processed.insertIgnore({ consumer: 'inventory', eventId });
  if (!claimed) return;
  await tx.stock.decrementWhereAvailable(orderId, sku, qty);
  await tx.outbox.insert(inventoryReservedEvent);
});

Event-driven architecture

High
Concept

The pipeline is a chain of observable state transitions, not a chain of hidden remote calls.

Why it works this way

Events decouple availability and scaling but demand contract governance, correlation, compensation, and end-to-end lag SLOs.

Example
Order Created → Payment → Inventory → Notification
Correlate every event with orderId, traceId, causationId, eventId, version, and occurredAt.
