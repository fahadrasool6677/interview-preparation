Shared orders/payments schema

High
Concept

The phase uses orders as the aggregate record and payments as child attempts, with checks, foreign keys, uniqueness, money in minor units, and UTC timestamps.

Why it works this way

A shared schema makes cardinality, integrity, transaction, and performance discussions concrete.

Running example
SQL
-- Shared schema used throughout this phase
CREATE TABLE orders (
  id bigint PRIMARY KEY,
  customer_id bigint NOT NULL,
  status text NOT NULL CHECK (status IN ('pending','paid','cancelled')),
  total_minor integer NOT NULL CHECK (total_minor >= 0),
  currency char(3) NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE payments (
  id bigint PRIMARY KEY,
  order_id bigint NOT NULL REFERENCES orders(id),
  provider_ref text UNIQUE,
  status text NOT NULL CHECK (status IN ('processing','succeeded','failed')),
  amount_minor integer NOT NULL CHECK (amount_minor >= 0),
  created_at timestamptz NOT NULL DEFAULT now()
);

SELECT o.id, o.status, p.status AS payment_status
FROM orders o LEFT JOIN payments p ON p.order_id = o.id
ORDER BY o.id;
Expected:
Orders remain visible without a payment.

  • Treating Shared orders/payments schema as a library setting instead of defining its failure and consistency behavior.
  • Ignoring retries, concurrency, observability, and trust boundaries in production.

SQL fundamentals

High
Concept

SQL is declarative: SELECT projects, FROM forms inputs, WHERE filters, GROUP BY aggregates, HAVING filters groups, and ORDER BY defines output order.

Why it works this way

The optimizer chooses physical execution, so correctness depends on relational semantics rather than procedural reading order.

Running example
SQL
SELECT id, total_minor
FROM orders
WHERE status = 'paid'
ORDER BY created_at DESC
LIMIT 2;

Joins

High
Concept

Joins combine rows by predicates. INNER requires matches; LEFT preserves the left side; join cardinality can multiply parent rows.

Why it works this way

Understanding one-to-many cardinality prevents incorrect totals and missing orders.

Running example
SQL
SELECT o.id, COUNT(p.id) AS attempts
FROM orders o
LEFT JOIN payments p ON p.order_id = o.id
GROUP BY o.id
ORDER BY o.id;

High
Concept

A subquery produces a scalar, row set, or correlated test. EXISTS is often the clearest way to express presence without row multiplication.

CTEs

High
Concept

A common table expression names an intermediate relation; recursive CTEs traverse hierarchies. Modern PostgreSQL may inline non-materialized CTEs.

Why it works this way

Window functions

High
Concept

Window functions compute across related rows without collapsing them. PARTITION BY defines groups and ORDER BY defines sequence.

Why it works this way

They solve ranking, running totals, and latest-per-group while preserving row detail.

Running example
SQL
SELECT order_id, id AS payment_id,
  row_number() OVER (PARTITION BY order_id ORDER BY created_at DESC, id DESC) AS attempt_no
FROM payments;

Transactions

High
Concept

A transaction commits related changes atomically. Keep it short, lock in a consistent order, and never wait on remote APIs while holding locks.

Why it works this way

Order transitions, payment rows, and outbox events must either become visible together or not at all.

Running example
SQL
BEGIN;
UPDATE orders SET status='paid' WHERE id=101 AND status='pending';
INSERT INTO payments(id,order_id,status,amount_minor) VALUES (501,101,'succeeded',4999);
COMMIT;

Both changes commit together; production code checks affected-row count.

Isolation levels

High
Concept

Read Committed prevents dirty reads; Repeatable Read gives a stable snapshot; Serializable rejects executions that cannot be ordered serially.

Locks

High
Concept

Row locks coordinate conflicting writes; SELECT ... FOR UPDATE explicitly locks selected rows. Lock scope and duration determine contention.

Why it works this way

A guarded order transition can serialize competing payment completions without locking unrelated orders.

Deadlocks

High
Concept

A deadlock is a cycle of transactions waiting on one another; the database aborts a victim.

Why it works this way

Applications must use deterministic lock order, short transactions, and bounded retry because detection cannot preserve both transactions.

Running example
SQL
BEGIN;
SELECT id FROM orders WHERE id IN (101,102)
ORDER BY id
FOR UPDATE;
Expected:
Every workflow locks orders in ascending ID order.

High
Concept

A composite index is ordered lexicographically; equality on leading columns followed by range/order columns is a common design.
