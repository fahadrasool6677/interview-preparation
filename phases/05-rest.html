Phase 05 · Production HTTP contracts

REST APIs

Design predictable order and payment APIs that remain correct under retries, concurrency, untrusted clients, and partial failure.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

REST principles

High
Concept

REST models resources with stable identifiers and manipulates representations through a uniform, stateless HTTP interface. Constraints include client/server separation, cacheability, layered systems, and hypermedia where useful.

Why it works this way

Uniform semantics reduce coupling: clients depend on resource contracts rather than server implementation or RPC-shaped controller names.

Running example
Example
POST /orders
GET /orders/ord_42
PATCH /orders/ord_42

Representation: { "id": "ord_42", "status": "pending" }
Expected:
Resource nouns, standard verbs, stateless requests
Common mistakes / interview traps
  • Treating REST principles as a library setting instead of defining its failure and consistency behavior.
  • Ignoring retries, concurrency, observability, and trust boundaries in production.
Interview questions
  • How would you apply REST principles to an order/payment API?
  • What failure mode changes your design for REST principles?
Reveal model answers
REST principles should be explained as a contract: state the invariant, the mechanism that preserves it, and the behavior under retry or partial failure.
For orders and payments, I make ownership, consistency boundaries, and externally visible errors explicit, then instrument the important decisions.
Senior follow-ups
  • What trade-off would make you reject the default REST principles approach?
  • How would you roll this out and prove it behaves correctly?
Reveal senior-level answers
I compare correctness, latency, operability, and cost. I prefer the simplest mechanism that preserves the business invariant and has a safe degradation path.
I use compatibility tests, staged rollout, metrics by outcome, structured audit events, and a rollback path; load and fault tests cover retries and dependency failure.

Design a production-ready REST principles decision for an order/payment endpoint. State the invariant, failure response, telemetry, and one rejected alternative.

HTTP methods

High
Concept

GET and HEAD are safe; PUT, DELETE, and safe methods are idempotent; POST is generally neither; PATCH semantics depend on the patch document.

Why it works this way

Method semantics let clients, gateways, retries, and caches behave correctly without application-specific knowledge.

Running example
Example
POST /orders              create
GET /orders/ord_42         read
PUT /orders/ord_42/address replace address
PATCH /orders/ord_42       partial transition
DELETE /orders/ord_42      cancel/remove
Expected:
Choose by semantics, not CRUD naming alone

HTTP status codes

High
Concept

Use status families consistently: 2xx success, 3xx redirection/cache validation, 4xx client-contract failure, and 5xx server/dependency failure.

Why it works this way

Sessions

High
Concept

A session keeps authentication state server-side and gives the client an opaque, rotating identifier.

Why it works this way

Server-side revocation and small browser credentials are useful, while a shared store is needed across instances.

Running example
Node.js

  await sessions.delete(req.session.id);
  res.clearCookie('__Host-session');
  res.sendStatus(204);

204 and the server-side session is invalidated

JWT

High
Concept

A JWT is a signed set of claims, not encrypted state. Verify algorithm, signature, issuer, audience, expiry, and purpose before trusting claims.

Why it works this way

Local verification can reduce an authorization-server lookup, but revocation and claim staleness become design concerns.

Running example
Node.js
const claims = await jwtVerify(token, key, {
  algorithms: ['RS256'], issuer: 'https://id.example', audience: 'orders-api'
});
if (claims.payload.typ !== 'access') throw new Error('wrong token type');

Only validated access-token claims reach authorization

Refresh tokens

High
Concept

Refresh tokens are long-lived credentials used only at the authorization server to mint new access tokens. Rotate them and detect reuse.

Why it works this way

Idempotency

High
Concept

Idempotency makes repeated requests with the same intent produce one business effect. Persist a client key, request fingerprint, state, and original response atomically.

Why it works this way

Networks lose responses and clients retry; exactly-once transport is unavailable, so the server must deduplicate effects.

Running example
Node.js
await db.transaction(async tx => {
  const prior = await tx.idempotency.findUnique({ key });
  if (prior) return replay(prior);
  const payment = await tx.payment.create({ orderId, amount });
  await tx.idempotency.create({ key, requestHash, response: payment });
});
Expected:
Concurrent duplicate keys resolve to one stored result

High
Concept

Why it works this way

CORS

High
Concept

CORS is a browser response-sharing policy. The server explicitly allows trusted origins, methods, and headers; credentialed requests require an exact origin.

Why it works this way

Same-origin policy blocks script access by default; CORS relaxes that boundary but is not authentication or a server-to-server firewall.

Running example
Node.js
const allowed = new Set(['https://shop.example']);
app.use(cors({
  origin(origin, cb) { cb(null, allowed.has(origin)); },
  credentials: true,
  methods: ['GET', 'POST']
}));
Expected:
Never combine credentials with reflected arbitrary origins
