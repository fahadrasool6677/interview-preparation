Docker & Deployment

Package, ship, secure, observe, and recover Node.js services with explicit operational trade-offs.

Interview shape: claim → mechanism → production example → failure → trade-off. Reveal answers only after you attempt them aloud.
On this page

Docker

High
Concept

Docker packages a process and its filesystem dependencies into an image, then runs it with namespace isolation and cgroup resource controls. Containers share the host kernel; they are not lightweight virtual machines.

Why it works this way

A consistent artifact reduces environment drift from laptop to CI to production. Isolation improves repeatability, but host kernel, storage, networking, and security still require explicit operational design.

Running example
Example
docker build -t orders-api:1.4.0 .
docker run --rm -p 3000:3000 --memory=512m --cpus=1 orders-api:1.4.0
Expected:
The immutable image runs with bounded CPU and memory.
Common mistakes / interview traps
  • Explaining Docker as syntax or tooling without discussing its runtime behavior.
  • Ignoring observability, rollback, resource limits, and failure recovery.
Interview questions
  • Where does Docker fit in a production Node.js system?
  • What failure mode would make you reconsider your Docker design?
Reveal model answers
Docker should solve a specific operational or engineering constraint. I would state that constraint, describe the mechanism, and then show how I verify the result in production.
I would reconsider the design when its failure domain, operating cost, or recovery time no longer meets the service's SLOs.
Senior follow-ups
  • How would you operate Docker safely during a partial outage?
  • Which metrics and trade-offs matter most for Docker?
Reveal senior-level answers
Prefer bounded retries, explicit timeouts, graceful degradation, and a tested rollback path. Preserve enough telemetry to distinguish application, dependency, and infrastructure failures.
Measure user-visible latency and errors first, then saturation, capacity, cost, and recovery time. Optimize only after identifying the binding constraint.
Exercise

Containerize a small Node.js API, apply CPU and memory limits, then observe its behavior under load and on SIGTERM.

Dockerfile

High
Concept

A Dockerfile is an ordered build recipe. Each filesystem-changing instruction creates a cacheable layer, while ENTRYPOINT and CMD define the runtime process.

Why it works this way

Instruction order controls cache reuse and rebuild speed. Exec-form commands deliver signals correctly, which is essential for graceful Node.js shutdown.

Running example
Example
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
USER node
EXPOSE 3000
CMD ["node", "server.js"]
Common mistakes / interview traps
  • Copying the whole repository before npm ci, invalidating dependency cache.
  • Using a shell-form CMD or running the service as root.

Docker Compose

High
Concept

Compose declares a multi-container development or single-host stack: services, networks, volumes, environment, health checks, and dependency relationships.

Why it works this way

It makes local infrastructure reproducible, but depends_on only orders startup unless health conditions are configured; the application must still retry unavailable dependencies.

Running example
Example
services:
  api:
    build: .
    ports: ["3000:3000"]
    depends_on:
      postgres:
        condition: service_healthy
  postgres:
    image: postgres:17-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10

Images

High
Concept

An image is a content-addressed, immutable manifest of read-only layers plus runtime metadata. Tags are mutable references; digests identify exact content.

Why it works this way

Layer reuse saves transfer and storage, while digest pinning makes a deployment reproducible and auditable.

Running example
Example
docker pull node:22-alpine
docker image inspect node:22-alpine --format '{{index .RepoDigests 0}}'
docker history node:22-alpine

Containers

High
Concept

A container is a running image plus a writable layer and runtime configuration. Its lifecycle should be disposable; durable state belongs outside it.

Why it works this way

Schedulers replace failed instances rather than repairing them. Stateless processes enable horizontal scaling and predictable recovery.

Running example
Example
docker run -d --name api --restart=on-failure:3 orders-api:1.4.0
docker inspect api --format '{{.State.Status}} {{.State.Health.Status}}'
docker stop --time 20 api

Volumes

High
Concept

Volumes persist data independently of a container writable layer. Named volumes are managed by Docker; bind mounts expose host paths directly.

Why it works this way

Container layers are ephemeral and inefficient for durable, write-heavy state. Volume ownership, backup, restore, and cross-host movement remain operator responsibilities.

Running example
Example
docker volume create pgdata
docker run --rm -v pgdata:/var/lib/postgresql/data postgres:17-alpine
docker volume inspect pgdata

Networks

High
Concept

User-defined bridge networks provide service-name DNS and isolated connectivity. Publishing a port exposes it through the host; EXPOSE alone is documentation.

Why it works this way

Separating internal dependency traffic from public ingress reduces attack surface and clarifies trust boundaries.

Running example
Example
docker network create backend
docker run -d --network backend --name redis redis:7-alpine
docker run --rm --network backend redis:7-alpine redis-cli -h redis ping
Expected:
PONG

Environment variables

High
Concept

Environment variables inject runtime configuration into an otherwise immutable artifact. Validate them at startup and distinguish configuration from secrets.

Why it works this way

Build-once/deploy-many avoids environment-specific images. Missing or malformed values should fail fast before the instance receives traffic.

Running example
Node.js
const required = ['DATABASE_URL', 'PORT'];
for (const key of required) {
  if (!process.env[key]) throw new Error('Missing ' + key);
}
const port = Number(process.env.PORT);
if (!Number.isInteger(port)) throw new Error('PORT must be an integer');
Common mistakes / interview traps
  • Baking secrets into image layers or committing .env files.
  • Logging the full environment or silently accepting invalid defaults.

Multi-stage builds

High
Concept

Multi-stage builds use separate build and runtime stages so compilers, source maps, test tools, and development dependencies need not ship in the final image.

Why it works this way

A smaller runtime image transfers faster and has less attack surface, while build reproducibility remains in the Dockerfile.

Running example
Example
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine AS runtime
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force
COPY --from=build /app/dist ./dist
USER node
CMD ["node", "dist/server.js"]

Production deployment

High
Concept

A production deployment promotes a versioned artifact through environments with readiness checks, controlled rollout, telemetry, and rollback.

Why it works this way

Deployments change both code and system behavior. Canary or rolling strategies limit blast radius, but only if health signals represent user-visible correctness.

Running example
Example
release: orders-api@1.4.0 (image digest pinned)
strategy: 10% canary -> 50% -> 100%
gates: readiness, p95 latency, 5xx rate, queue lag
rollback: automatic on SLO breach

PM2

High
Concept

PM2 supervises Node.js processes, supports restart policies, logs, graceful reload, and cluster mode. Under a container orchestrator, process supervision is often delegated to the platform.

Why it works this way

On a VM, PM2 can improve availability and use multiple cores. In containers, one process per container usually gives clearer lifecycle and scaling semantics.

Running example
Example
module.exports = {
  apps: [{
    name: 'api',
    script: 'dist/server.js',
    instances: 'max',
    exec_mode: 'cluster',
    kill_timeout: 15000,
    max_memory_restart: '500M'
  }]
};

Reverse proxy

High
Concept

A reverse proxy terminates client connections and forwards requests to upstream services, often adding TLS, routing, buffering, compression, and rate limits.

Why it works this way

Central ingress policy simplifies applications, but incorrect timeout and buffering settings can break streaming, WebSockets, uploads, and cancellation.

Running example

Forward: Host, X-Request-ID, X-Forwarded-For, X-Forwarded-Proto

Nginx

High
Concept

Nginx is an event-driven web server and reverse proxy commonly used for TLS termination, static files, routing, caching, and load balancing.

Why it works this way

It handles large numbers of mostly idle connections efficiently and shields application instances, but config must preserve client identity and request semantics.

Running example
Example
upstream api { server api:3000; keepalive 32; }
server {
  listen 80;
  location /api/ {
    proxy_pass http://api;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Request-ID $request_id;
  }
}

HTTPS

High
Concept

HTTPS is HTTP over TLS, providing server authentication, confidentiality, and integrity. Certificates bind names to public keys and require renewal.

Why it works this way

TLS prevents passive reading and active modification in transit. Correct termination, redirect, HSTS, modern protocols, and internal trust boundaries all matter.

Running example
Example
curl -I https://api.example.com/health
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null

Inspect certificate chain, negotiated protocol, and security headers.

CI/CD

High
Concept

Continuous integration validates each change; continuous delivery produces a releasable artifact; continuous deployment promotes passing changes automatically.

Why it works this way

Automated, repeatable gates shorten feedback and reduce manual drift. Security scans and tests help, but deployment safety also needs staged rollout and production signals.

on approved release:

Basic cloud architecture

High
Concept

A typical cloud service places DNS and CDN/WAF before a load balancer, runs stateless application instances across failure zones, and uses managed data, queue, cache, and object storage services.

Why it works this way

Managed primitives reduce undifferentiated operations, while multi-zone placement and asynchronous boundaries improve resilience. Every dependency still needs explicit timeout, retry, capacity, and cost design.

Running example
Example
DNS -> CDN/WAF -> Load Balancer -> Node instances (multi-AZ)

                                  |-> Queue -> workers
                                  |-> Managed Postgres
                                  |-> Object storage
Telemetry -> logs, metrics, traces, alerts
