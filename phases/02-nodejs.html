Node.js architecture

High
Concept

Node combines V8, Node core bindings, libuv, and an event-driven JavaScript API. JavaScript normally runs on one thread while the OS and libuv perform concurrent work.

Why it works this way

The architecture keeps coordination cheap for I/O-heavy services while delegating expensive or blocking operations to kernels, pools, workers, or child processes.

Running example
Node.js
const { versions } = process;
console.log(Boolean(versions.v8), process.release.name);
Expected:
true node
Common mistakes / interview traps
  • Explaining Node.js architecture only by syntax and not by runtime behavior.
  • Ignoring failure modes, observability, and the order/payment-service impact.
Interview questions
  • Explain Node.js architecture and give a production example.
  • What bug would reveal a weak understanding of Node.js architecture?
Reveal model answers
Node.js architecture is not just syntax; I explain its runtime mechanism, then show where it affects correctness or latency in an order or payment flow.
I would reproduce the behavior with a minimal case, add focused telemetry, and verify the fix under concurrency rather than relying on intuition.
Senior follow-ups
  • What trade-offs would make you avoid or constrain Node.js architecture in a high-throughput service?
  • How would you test and observe this behavior in production?
Reveal senior-level answers
I choose based on correctness, operational cost, team familiarity, and measurable workload characteristics. I make assumptions explicit and preserve a rollback path.
I use deterministic unit tests where possible, integration tests at boundaries, load or fault tests for concurrency, and metrics plus structured logs for production evidence.

libuv

High
Concept

libuv provides the event loop, cross-platform async I/O, a thread pool for selected APIs, timers, and process/signal abstractions.

Network I/O usually uses OS readiness mechanisms; file, DNS, crypto, and compression work may use the finite pool and contend.

Node.js event loop

High
Concept

Node advances through timer, poll, check, and close phases, with microtasks and process.nextTick handled at defined boundaries.

Why it works this way

Phase ordering enables efficient readiness polling; excessive callbacks, nextTicks, or synchronous work inflate latency for every connection.

Running example
Node.js
setImmediate(() => console.log("check"));
setTimeout(() => console.log("timer"), 0);
process.nextTick(() => console.log("nextTick"));
Expected:
nextTick
(timer/check ordering can vary by context)

Worker threads

High
Concept

Workers run JavaScript in separate V8 isolates and threads. They communicate through messages, transferred buffers, or carefully synchronized shared memory.

Why it works this way

They provide CPU parallelism without a separate process, but startup, serialization, memory, and coordination costs require a bounded pool.

Running example
Node.js
const { Worker, isMainThread, parentPort } = require("worker_threads");
if (isMainThread) new Worker(__filename).on("message", console.log);
else parentPort.postMessage(6 * 7);
Expected:
42

Streams

High
Concept

Streams process data incrementally through readable, writable, transform, and duplex interfaces. pipeline coordinates errors and cleanup.

Why it works this way

Backpressure bounds buffering when producers outpace consumers, protecting memory during uploads, exports, and proxying.

Running example
Node.js
const { Readable, Transform } = require("stream");
Readable.from(["pay", "ment"]).pipe(new Transform({ transform(c,e,cb){ cb(null, c.toString().toUpperCase()); } })).on("data", c => process.stdout.write(c));

PAYMENT

Medium
Concept

EventEmitter provides synchronous in-order local publish/subscribe. Listener exceptions propagate synchronously and error has special semantics.

Why it works this way

bus.once("paid", id => console.log(id));

Graceful shutdown

High
Concept

Mark unready, stop accepting work, drain requests and consumers, close dependencies, then force exit after a bounded deadline.

Why it works this way

A staged shutdown preserves availability and at-least-once correctness while preventing indefinitely stuck deployments.

Running example
Node.js

process.once("SIGTERM", () => { accepting = false; console.log("draining"); });
process.emit("SIGTERM");

draining

CPU-bound vs I/O-bound

High
Concept

I/O-bound work spends time waiting and fits event-driven concurrency. CPU-bound work occupies the JavaScript thread and delays unrelated requests.

Why it works this way

Workload shape, not language fashion, determines fit; CPU work belongs in workers, processes, services, or optimized native systems.

Running example
Node.js

while (Date.now() - start < 10) {}
setTimeout(() => console.log("I/O callback delayed"), 0);

I/O callback delayed

High
Concept

cache.delete("o1");
console.log(cache.size);

0
